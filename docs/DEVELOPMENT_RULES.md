# 공통 개발 규칙

우리 팀 5명이 모두 지키는 규칙입니다. AI 코딩 도구(Claude Code · Codex)도 같은 규칙을 따릅니다.
AI 가 읽는 원문은 [AGENTS.md](../AGENTS.md) 이고, 이 문서는 사람이 읽기 쉽게 **같은 번호로** 이유와 예시를 붙인 것입니다.
규칙을 바꾸려면 두 파일을 같은 PR 에서 함께 고칩니다.

## 규칙 1~15

### 1. 먼저 읽고 바꾼다
**왜:** AI 는 파일을 안 읽고도 그럴듯한 코드를 씁니다. 이미 있는 함수를 또 만들거나 규칙을 어기기 쉽습니다.
**이렇게:** AI 에게 일을 맡길 때 "먼저 관련 파일을 읽고, 무엇을 바꿀지 알려 줘" 라고 시작합니다.

### 2. 변경 범위를 먼저 말한다
**왜:** 범위가 넓어지면 PR 리뷰가 어려워지고 다른 사람 코드와 부딪힙니다.
**이렇게:** "어떤 파일을 왜 바꿀지 목록으로 먼저 보여 줘" → 확인 → 진행. 요청하지 않은 파일이 바뀌었으면 되돌립니다.

### 3. 다른 팀원 담당 모듈은 건드리지 않는다
**왜:** 같은 파일을 두 사람이 고치면 충돌이 나고, 서로의 의도를 덮어씁니다.
**이렇게:** 담당자가 정해지면 [TEAM_GUIDE.md](TEAM_GUIDE.md) 의 담당표에 적습니다. 남의 모듈을 고쳐야 하면 담당자에게 먼저 말합니다.

### 4. 공통 계약을 임의로 바꾸지 않는다
**왜:** 백엔드 필드 이름 하나를 바꾸면 프론트 · 테스트 · 다른 팀원 코드가 한꺼번에 깨집니다.
**계약 파일:** `backend/app/contracts/`, API 경로, 이벤트 타입 · 상태값, `contracts/`, `frontend/src/api/schema.d.ts`
**이렇게:** [TEAM_GUIDE.md — 공통 API 를 바꿔야 할 때](TEAM_GUIDE.md#공통-api-를-바꿔야-할-때) 절차대로 합니다.

### 5. DB 스키마 변경은 마이그레이션과 함께
**왜:** 마이그레이션 없이 모델만 바꾸면 다른 팀원 DB 와 모양이 달라져 "내 PC 에선 되는데" 가 생깁니다.
**이렇게:** [TEAM_GUIDE.md — DB 컬럼을 추가해야 할 때](TEAM_GUIDE.md#db-컬럼을-추가해야-할-때). CI 의 `alembic check` 가 빠뜨린 것을 잡습니다.

### 6. 도메인 지식은 `domains/` 에만
**왜:** BUILDWISE 의 핵심은 "같은 엔진에 다른 기업 · 다른 상품을 붙인다" 입니다. 엔진에 "GPU" 같은 말이 들어가면 그 주장이 깨집니다.
**이렇게:** CPU · GPU · 랙 같은 말은 `backend/app/domains/hardware/` 에만 씁니다. `agents/` · `workflows/` 에는 쓰지 않습니다.

### 7. 이벤트와 결과 저장 규칙을 지킨다
**왜:** 이 규칙 덕분에 늦게 도착한 옛 결과가 최신 결과를 덮지 않고, 이벤트 순번에 빈 번호가 생기지 않습니다.
**이렇게:** 이벤트는 `append_event`, 실행 결과 저장은 `WorkflowRunner._guarded` 안에서, DB 조회에는 항상 `company_id` 조건. 이유는 [ARCHITECTURE.md §3](ARCHITECTURE.md#3-실행-흐름).

### 8. 구현 뒤 테스트를 실제로 돌린다
**왜:** "코드를 썼다" 와 "동작한다" 는 다릅니다. 완료 기준은 테스트 통과입니다.
**이렇게:** PR 전에 `scripts/check.ps1`(또는 `check.sh`). 실패하면 숨기지 말고 PR 에 적습니다. 테스트를 지우거나 건너뛰게 바꾸지 않습니다.

### 9. 의존성은 확인 뒤에, 정확한 버전으로
**왜:** 버전이 `^1.2` 처럼 열려 있으면 팀원마다 다른 버전이 깔려 결과가 달라집니다. 큰 라이브러리는 배우는 비용도 큽니다.
**이렇게:** 팀 채팅에 "이 패키지 넣어도 될까요?" → 동의 → `uv add "이름==1.2.3"` 또는 `npm install -E 이름@1.2.3` → lockfile 도 커밋.

### 10. 공유 설정 파일을 다시 만들지 않는다
**왜:** AI 가 오류를 고친다며 `package.json` · `compose.yaml` 을 통째로 새로 쓰면 다른 사람 환경이 깨집니다.
**이렇게:** 필요한 줄만 고치고 PR 에 "공유 설정을 건드림" 을 체크합니다.

### 11. 비밀값 · 개인정보를 커밋하지 않는다
**왜:** 이 저장소는 **공개** 저장소입니다. 올라간 키는 지워도 기록에 남습니다.
**이렇게:** API 키는 `.env` 에만(커밋 안 됨). 커밋 이메일은 GitHub noreply 주소로([START_HERE.md 3단계](START_HERE.md#3-git-설치--내-이름-설정)). CI 의 gitleaks 가 검사합니다.
키를 실수로 올렸으면 **바로 그 키를 폐기 · 재발급**하고 팀에 알립니다(기록에서 지우는 것만으로는 부족합니다).

### 12. 프로젝트를 새로 만들지 않는다
**왜:** 오류가 났을 때 AI 가 `npm create vite` 로 새로 만들면 팀의 구조 · 계약 · 테스트가 다 사라집니다.
**이렇게:** [TROUBLESHOOTING.md](TROUBLESHOOTING.md) → 팀원에게 질문 순서로 해결합니다.

### 13. 데이터를 지어내지 않는다
**왜:** 실제 제품 가격 · 사양을 지어내면 시연에서 사실과 다른 정보를 보여 주게 됩니다.
**이렇게:** 확인 못 한 가격은 `price_status: unconfirmed`, 출처 없는 데이터는 `data_status: unverified`. 견본 데이터는 가상 브랜드로 만들고 `test` 로 표시합니다.

### 14. 화면 상태는 이벤트로만 바꾼다
**왜:** 기업 담당자에게 보여 주는 화면이 실제 처리 상태와 다르면 시연 전체가 신뢰를 잃습니다.
**이렇게:** 애니메이션도 `OfficeState` 를 보고 움직이게 합니다. 시간이 지났다고 '완료' 로 바꾸지 않습니다.

### 15. 작업 하나 = 기능 브랜치 하나 = PR 하나
**왜:** `main` 은 언제나 돌아가는 상태여야 합니다. 작업을 작게 나눌수록 충돌이 적습니다.
**이렇게:** [TEAM_GUIDE.md](TEAM_GUIDE.md) 의 순서대로. `main` 은 보호돼 있어 직접 푸시가 막힙니다.

## Git 규칙 요약

| 항목 | 규칙 |
|---|---|
| 브랜치 | `main` 하나 + 짧은 기능 브랜치. `develop` 브랜치는 쓰지 않습니다 |
| 브랜치 이름 | `종류/영역-내용` — 예: `feat/office-desk-log`, `fix/quote-total`, `docs/start-here-mac`, `chore/ci-cache` |
| 커밋 메시지 | 한국어로 무엇을 했는지 한 줄. 예: `견적 표에 할인 금액 줄 추가` |
| PR | 리뷰 1명 승인 + CI 통과 뒤 **Squash and merge** |
| 병합 뒤 | 그 브랜치는 끝. 다음 작업은 최신 `main` 에서 새 브랜치를 만듭니다 |
| 크기 | PR 하나는 되도록 파일 10개 이하 · 하루 안에 리뷰할 수 있는 크기 |

`develop` 을 두지 않는 이유: 5명이 7주 동안 쓰기에는 통합 단계가 하나 더 생기는 비용이 더 큽니다.
대신 `main` 보호(PR 필수 · CI 통과 필수 · 승인 1명)로 `main` 을 지킵니다.

## 담당 모듈 정하는 법

역할이 정해지면 [TEAM_GUIDE.md](TEAM_GUIDE.md) 의 담당표를 채우고, 원하면 `.github/CODEOWNERS` 파일을 만들어
그 폴더를 바꾸는 PR 에 담당자가 자동으로 리뷰어로 들어가게 합니다.

```text
# .github/CODEOWNERS 예시 (GitHub 아이디를 넣습니다)
/backend/app/agents/        @담당자아이디
/frontend/src/features/office/  @담당자아이디
```
